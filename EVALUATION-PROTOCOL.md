# Evaluation protocol — a PIP configuration reflected at runtime, a hardware change proposed as a model change

Status: v1.1 (2026-09-23). Task: `docs/CLAUDE-CODE-PROMPT-evaluation-minimal.md`. Everything under `evaluation/`
(overview in `README.md`, commands in `RUNNING.md`). Results of the first unattended simulated runs: `results/rq1.csv` (RQ1, 30 rows, evidence
under `runs/sim-2026-09-23/`) and `results/rq2.csv` (RQ2, 3 domains × 8 steps, evidence under `runs/rq2-2026-09-23/`),
§11. Hardware (attended, the two Raspberry Pis with real bricklets): RQ1 rows office-01, home-01, fitness-01 in
`results/rq1.csv` and RQ2 on the three domains in `results/rq2.csv` (run `hw-2026-09-24`, evidence under
`runs/hw-2026-09-24/`).

## 1. Research questions and what counts as evidence

**RQ1 — a PIP configuration is reflected at runtime, in three domains, without code changes.** Subjects: the one
metamodel, the three domain models of the demo (office, smart home, fitness centre) and **30 level-0 models**,
ten per domain. Code, images and settings are identical for every row; only the model changes. A row passes
only if all four checks pass:

| check | claim | how it is verified |
|---|---|---|
| RQ1.1 twin | the decisions of each twin are those the configuration prescribes | every probe tag on every device: the twin's decision reason (`/twin/current` → `context.auth.reason`) equals the oracle's, and the fleet audit (`GET /api/pip/decisions`) carries the same decision from the device |
| RQ1.2 fleet | the knowledge each twin receives is scoped to the space it guards; indicators, sensors and goals known to the federation are those of the model | the device bundle (`GET /api/pip/devices/{id}/bundle`) lists **exactly** the principals holding a role allowed on that space (an extra principal fails as much as a missing one), its allowed roles and staleness; the fleet resolves each device to the modelled space (`/api/pip/status`); `/api/kpis/sensors`, `/api/kpis` (source `model`) and `/api/pip/projection` list the model's sensors, indicators with their inputs, and goals |
| RQ1.3 injection | a statechart defined at fleet level is distributed to every twin and enacted by the device | the fleet distributes `eval-signature` (beep **1777 Hz** + amber on `TAG_DETECTED`, no authorization); a tap on each device reaches `s_sig` and the device-api reports `speaker.lastCommand.params.frequency = 1777` |
| RQ1.4 override | one twin runs its own statechart instead, without affecting the others, and can be brought back | `fork-local` on the second twin + its own chart at **1999 Hz**; taps: first twin 1777, second 1999; `/api/fleet-machines/inheritance` = `inheriting` / `overriding`; `inherit` → 1777 and `inheriting` again |

**RQ2 — a hardware change is detected, proposed as a model change, and its inconsistencies surfaced.** One model
per domain, eight steps (§6), each recording the runtime effect the fleet shows, the assistant's proposal and the
outcome of applying it (the commit's status and the conformance of the committed model), including the case where
the commit **must be blocked**.

**Expected outcomes never come from the code under test.** Each configuration is an *intent* (`intents/*.json`);
the model is built from it and the expectations are derived from it by an independent oracle (§4).

## 2. The subjects

### 2.1 Intents → models

`intents/<domain>-NN.json` is the source of a row. Row 1 of each domain restates the demo model (same people,
spaces, policies, devices, sensors, indicators, goals; the home and gym seeds have one device, the stack has two,
so a second reader of the same type guards a second space). Rows 2–10 are generated by a PRNG seeded from the row
id (`eval/<domain>/NN`, reproducible), varying:

- principals (3–8, plus an *outsider* and, in odd rows, a *revoked* one) and the roles each holds (1–2);
- roles (2–4 of the domain's role types; one type is always kept for the outsider role no permit grants);
- spaces (3–7) and containment depth (1–3: a root zone, an optional inner zone, an optional third level, rooms);
- policies (2–6 permits with 0–2 windows on random spaces; **every even row adds a deny on an ancestor of the
  first device's room**, so a permit below it is overridden);
- time windows (`NOW`, `NOT_NOW`, `ALWAYS`, §2.3), validity (`VALID`, `VALID_PAST`, `VALID_FUTURE`, `EXPIRED`,
  `NOT_YET_VALID`), revocation;
- staleness per space (none, `allow-cached` 1 h, `deny` 24 h, root 2 h);
- devices (always the two of the stack, guarding two rooms at different depths when the tree allows);
- sensors (office: 1–5 typed keys per device; home and gym: none — their domain models type no sensor, and RQ1
  does not change domain models), indicators (office: 0–2 over shared keys, `avg`/`max`/`min`) and goals (office: a
  typed goal on the sensing device's room or its parent; home/gym: an untyped goal or none).

Fix-ups keep every row informative: each device has a principal expected `ok` and one expected
`unknown_credential`; when a `NOT_NOW` window exists a role granted only during it gives an `outside_hours` probe.
`npm test` asserts: 30 unique model names and ids (no collision with the seeds), every model conformant
(`check`, `projectable: 'error'`) and projectable, every device with an `ok` and an `unknown_credential` probe.

The model is built with the seeds' own builder (`mlm-core/fixtures`: ids derived from names), typed by the
domain's **existing** O1 and stored in the domain's **existing** Studio project — nothing of the demo seeds is
edited (`git diff --exit-code` on the fixtures and goldens is part of the verification). `models/` holds every
model built at the reference instant (2026-09-23 10:00 Europe/Rome) with its expectations.

### 2.2 Placeholders

Device ids are `EVAL-ACS-1` / `EVAL-ACS-2` and tags `EVAL-TAG-n`. The simulated engines announce those ids and the
mock tap accepts any string, so the simulated rows use the models literally. For the hardware rows the loader
substitutes the real X-Device-Ids and the four physical UIDs from `prod-devices.env` (never committed; the
`.example` lists the names); hardware probes are limited to `EVAL-TAG-1..4`.

### 2.3 Anchoring in time

Taps are evaluated at the wall clock in `Europe/Rome` and no probe can set the time (trap 3), so windows and
validity are symbolic and resolved when the row is loaded (T0): `NOW` = today's weekday, T0−1 h → T0+4 h;
`NOT_NOW` = a one-hour slot of the same weekday ending 2 h before T0 (or starting 5 h after it before 03:00);
`ALWAYS` = every day; `EXPIRED` = `validTo` yesterday, `NOT_YET_VALID` = `validFrom` tomorrow, `VALID_PAST` /
`VALID_FUTURE` = 30 days either side. A row must finish within the NOW window (it takes ~1.6 min; the margin is
recorded in `load.json`). The resolved model is saved with the row's evidence.

## 3. The stack

Same images as production, the evaluation overrides stacked on the production compose files
(`stack/*.override.yml`): the fleet and the two devices on their own volumes (`evaluation/data/*`, git-ignored),
Mode B (the compose default), the fleet pointed at the cloud Studio with the fleet's operator account, no device →
space fallback (the model decides through the announced X-Device-Id). Simulated rows: the mock device-api
(`deploy/config.mock.yml`; RQ2: `stack/config.mock.rq2.yml`, without the `ambient` and `soundPressure` bricklets
so they can be plugged live). Hardware rows: the production device configs against the Pis' brickd
(`ACS*_BRICKD_HOST`), the real ids. The fleet is pointed at a row's model with `PUT /api/pip/settings`.

## 4. The oracle (`src/gen/expected.ts`)

From the intent alone: allowed roles of a space = roles granted by a permit on the space or an ancestor minus roles
denied by a deny on the space or an ancestor (deny overrides permit across the containment chain; priority plays
no part — trap 2). A device's bundle holds the principals with an allowed role. A tap of a principal not in the
bundle is `unknown_credential` (never `no_role` — trap 1); otherwise `revoked`, then `expired` / `not_yet_valid`,
then `ok` when one allowed role is granted by a permit whose windows cover T0 (a permit without windows = always),
else `outside_hours`. Staleness = the first declared along the chain, else the default (1 h, deny). Sensors, KPI
inputs and goals are read off the intent. The oracle is unit-tested on the seed rows against the demo's documented
outcomes.

## 5. RQ1 procedure per row (`src/runner/rq1.ts`)

1. **Load** — the model is created through the Studio's real write path: an empty level-0 model row (PostgREST, as
   the operator) filled by one `commit-model` call carrying every element as create ops, so the conformance gate,
   the projection build and the version bump are the Studio's own. `T_commit` = the `changes.at` of that commit
   (DB clock; the offset to the runner's clock is estimated around the call and recorded).
2. **Switch** — `PUT /api/pip/settings {modelId}`; wait for `/api/pip/status.sync` on the model with `appliedAt`
   after the commit (**M1a**); wait for each device's cache file (`evaluation/data/<dev>/pip-cache.json`, the
   engine runs on the laptop in both modes) to carry the model with `fetchedAt` after the commit (**M1** = the last
   device's fetch − T_commit).
3. **RQ1.2** — the checks of §1 against the oracle.
4. **RQ1.1** — for each device and probe: wait for `s_idle` (taps are accepted only there, G6; three attempts),
   tap (`POST <device-api>/api/nfc/mock/tag/{uid}`, the reader path; hardware: the runner prompts for the physical
   tap), watch `/twin/stream` for the decided state, read the reason, confirm the audit entry. **M3** = the
   engine's snapshot instant of the first state that actuates (the beep of `s_read`) − the reader event instant
   (`nfc.status.reader.at` of the device-api): two processes on the same host clock.
5. **RQ1.3** — `PUT /api/fleet-machines/eval-signature`, activate, `POST /api/fleet-machines/apply?force=true`;
   **M2** = the last twin's `machineSince` (the twin snapshot reports the running machine and its load instant) −
   the apply request; a tap per device must yield `s_sig` with the speaker at 1777 Hz.
6. **RQ1.4** — `POST /api/devices/acs2/fork-local`, then `PUT <engine acs2>/api/machines/local-eval-signature`
   (1999 Hz) and activate; taps on both; inheritance status; `POST /api/devices/acs2/inherit`; tap; status.
   Both engines are put back on `access-occupancy`.
7. **Verdict and evidence** — `results/rq1.csv` (one row: pass, the four checks, probes, M1, M1a, M2, M3 median
   and sample count, load instant) and `runs/<run>/<row>/` (model, expectations, every response, `checks.json`,
   `log.txt`).

At the end of a run the evaluation models are deleted (management API) and a checksum of the demo models (ids,
versions, element counts) is compared with the one taken before the run.

## 6. RQ2 procedure per domain (`src/runner/rq2.ts`)

Setup: a copy of the domain model (`EvalOfficeBuilding` — without `SoundLevelSensor`, so a key with no type
exists in the office too —, `EvalSmartHome`, `EvalFitnessCentre`) in the same Studio project; the fleet's
operator elevated to admin for the level-1 commits (restored at the end); a level-0 model with two devices
(`dev1` in `room_a`, `dev2` in `room_b`; the office devices start with the three sensors of the `co2` bricklet
modelled). Proposals are computed with `suggest()` of `mlm-core` — the function the Studio runs — over the live
`device_observations` rows the fleet writes, asked on both models the operator would open (the level-0 model, where
the A rules fire, and the domain-model copy, where the B rules fire); applying one commits its ops through
`commit-model`. A2 is one proposal per device (all its unmodelled keys at once); B2 one per untyped key.
**M4** = the change instant → `updated_at` of the observation row carrying the change.

Every domain starts from the boot topology: the device containers are re-created after a domain (hardware: the
operator unplugs the bricklets) and the runner waits until the fleet observes both devices online, under their boot
id, without `illuminance`/`decibel` — the fleet keeps a device's last readings while it is offline, and writes them
for the new model at the switch.

| # | change | expected runtime effect | expected proposal | applying it |
|---|---|---|---|---|
| 1 | plug `ambient` (key `illuminance`) on dev1 | new key observed, not modelled | office: A2 `SENSOR_UNMODELLED`; home/gym (no sensor type at all): A4 `TYPES_MISSING_ABOVE` + B2 `SENSOR_TYPE_MISSING[illuminance]` — with B2 for the three keys of the `co2` bricklet present since boot and B3 `KPI_TYPE_MISSING`; the operator accepts every type, then A2 for each device | committed, conformant |
| 2 | plug `soundPressure` (`decibel`, untyped everywhere) on dev1; then both bricklets on dev2 | keys observed | A4 + B2 `[decibel]` at the domain-model copy, then A2 for dev1; one A2 for dev2 creating both sensors | committed, conformant |
| 3 | the operator models `decibel.max` (dev1 + dev2), `illuminance.avg` (dev1) and the goal `roomLight` measuring it | both indicators known to the fleet (source `model`) | none | committed (B3/goal type added to the copy when missing) |
| 4 | unplug dev2 `ambient` (used by nothing) | sensor offline | none — the assistant does not propose removals; the operator deletes it | accepted, conformant |
| 5 | unplug dev2 `soundPressure` (one of two inputs of `decibel.max`) | `decibel.max` disabled (`dev2_decibel offline`) | none; the operator deletes the sensor | accepted; the indicator is decided again on one input |
| 6 | unplug dev1 `ambient` (the only input of `illuminance.avg`, measured by the goal) | `illuminance.avg` disabled | none; the operator tries to delete the sensor | **blocked**: 422 `not_conforming` with `P5.NO_INPUTS` (and `P6.GOAL_OUT_OF_SCOPE`), version unchanged |
| 7 | replace the controller of dev2 (its engine restarted announcing `EVAL-ACS-2B`) | the fleet announces the new id, dev2 unmapped (no space, no bundle) | A1 `DEVICE_UNMODELLED` with the choice "use dev2" | committed; dev2 mapped again, bundle back |
| 8 | re-plug dev2 `ambient`, then unplug it before accepting | key observed, then gone | A2 appears, then disappears (`suggest` is pure) | nothing committed |

Hardware: the same sequence with real bricklets (the device-api discovers a plugged bricklet by auto-configure;
unplugging is physical); the runner prompts and observes; step 7 restarts the engine container.

## 7. Measurements

| id | from → to | instants |
|---|---|---|
| M1 | model commit → bundle refreshed on the last device | `changes.at` (DB) → `fetchedAt` of the device cache carrying the version (host clock), per device, max |
| M1a | model commit → fleet applied | `changes.at` → `/api/pip/status.sync.appliedAt` |
| M2 | fleet apply → statechart active on the last twin | the apply request (runner) → `machineSince` of each twin (engine clock, same host), max |
| M3 | reader event → first actuation | `nfc.status.reader.at` → the snapshot instant of the first actuating state, both on the device's host clock |
| M4 | hardware change → proposal shown | the change request (runner) → `device_observations.updated_at` (DB) of the row carrying it; the proposal is computed on that row |

Clocks: M2 and M3 use one host clock (containers of one laptop; the engines run on the laptop in both modes).
M1 and M4 cross the DB clock; the offset measured around each load (`load.json.clockOffsetMs`, one round trip, so
≈ ±1 s) is applied — an M4 of a few hundred milliseconds, even slightly negative, means "within the same
observation cycle" rather than a measured latency.

## 8. What was added to the system for the evaluation (own commit, additive)

- `GET /api/pip/status.sync.appliedAt` — when the fleet swapped in the projection version it serves.
- The twin snapshot (`GET /twin/current`, the fleet's `/api/devices` snapshot, `/api/fleet/stream`) reports
  `machine` (the engine's store name of the running chart: `fleet-…` when distributed, `local-…` when forked) and
  `machineSince`; `POST /api/fleet-machines/apply` returns `appliedAt` per activated device.

No public contract changed: `pip-projection/1`, the device bundle and the rules API are untouched.

Not an addition but a prerequisite found while running RQ2: the cloud edge functions (`commit-model`, `projection`,
`export-model`) are deployed by hand (`pip-studio/README.md`), and the deployed `commit-model` predated the P5/P6
rules (its bundle of mlm-core was three days older than the sources), so step 6 was blocked by the multiplicity
rule alone (`C8.TOO_FEW`) and not by `P5.NO_INPUTS`. The three functions were redeployed from the current sources
on 2026-09-23 before the recorded run; the run is therefore an evaluation of the committed code.

## 9. Traps checked against the code

1. The bundle ships only principals holding a role allowed on the space (∪ permit restrictions): the oracle
   expects `unknown_credential`, not `no_role`, for anyone else — confirmed on every row.
2. Deny overrides permit across the whole containment chain; `priority` is never read by the decision.
3. No probe time: symbolic windows anchored at load (§2.3).
4. The mock tap (`/api/nfc/mock/tag`) is refused when `device.mock=false`; hardware probes are physical taps.
5. Home and fitness type no sensor: their rows carry none, and RQ2 exercises the untyped-key path there (and in
   the office through the copy without `SoundLevelSensor`).
6. The `co2` bricklet carries `co2`, `temperature` and `humidity`: RQ2 keeps it on the office devices as three
   modelled sensors and unplugs single-key bricklets (`ambient`, `soundPressure`) where one key must go.
7. `fork-local` copies the running chart under `local-…`: RQ1.4 adds a `PUT` on the engine for the 1999 Hz chart.

## 10. Threats and limits

- Simulated readings and taps are mock endpoints; the hardware rows (row 1 of each domain, RQ2 on the same) are
  the only ones with real bricklets and are attended.
- One laptop hosts the fleet and both engines: M1/M2/M3 exclude LAN latency between controller and fleet.
- The oracle re-states the documented semantics; a shared misreading of the semantics in oracle and system would
  not be caught. The seed-row tests tie the oracle to the outcomes the demos document.
- RQ2's proposals are computed by the harness calling `suggest()` on the same inputs the Studio reads (the model
  bundles and the `device_observations` rows); the Studio's rendering of them is not exercised. Applying a proposal
  goes through the real `commit-model`, so the conformance gate is the deployed one (§8).
- The fleet's runtime tables are written by the fleet's own account: writing for a model that no longer exists
  (403) makes its writers back off for 60 s. The runner parks the fleet on a demo model before deleting the RQ2
  models; a run that is killed mid-way leaves the models and the elevated role behind (`npm run eval -- clean`).

Hardware constraint found on the way: the HAT Brick's brickd detects a hot-plugged bricklet only on ports that
were occupied when brickd started. Before an attended RQ2 run every port the run uses must hold its bricklet at
brickd start (`sudo systemctl restart brickd` on each Pi with `ambient` and `soundPressure` plugged), then they are
unplugged for the boot state. Two earlier attempts the same afternoon stopped at step 2 on ACS-2 for this reason
and are not in the results.

**Redaction of the published evidence.** The physical tag UIDs never appear in the repository: in the hardware
evidence each is replaced by its label (`TAG_1`…`TAG_4`, `TAG_OTHER` for the unknown-card probe), as in
`prod-devices.env`. Personal and institutional names are neutralised in `evaluation/`: the seed row's first principal
is `davide`, the demo office models are called `office-demo` / `office-demo-minimal`, and the demo checksum is
logged by model id prefix. The evidence was edited as text only, so the element ids recorded in it are the ones of
the models as run, which differ from the regenerated `models/office-01.*` for that principal.
